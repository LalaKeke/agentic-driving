# T4 轨迹核验：工具接口

机器定义：`schemas/T4.schema.json`。本工具不信任“求解成功”标签，也不只检查 T2 给出的走廊，而是从原始米制场景重新检查车身与目标占用。

## 输入

`payload.scene`、`decision`、`corridor`、`trajectory` 必须全部提供。检查同一场景版本、坐标、参考时刻和预测网格。仅支持直线前进、零航向、零曲率、分段恒加速度的当前参考剖面。

## 输出：payload.verification

| 字段 | 含义 |
|---|---|
| `metadata` | 原场景版本与来源 |
| `verdict` | `PASS` 或 `FAIL` |
| `violations[]` | 每项包含错误码、对象、相对时刻、自车位置、计算值、阈值、单位、原因及修订请求 |
| `minimum_clearance_m` | 整个轨迹中区间包络间距的最小值；无障碍时为 `null`，不以无穷大写入 JSON |
| `checked_until_s` | 已遍历检查的相对时间上界；`FAIL` 时不表示此前区间可安全执行 |
| `released_prefix_s` | 通过时为允许执行的短前缀；失败固定为零 |
| `claim` | 固定 `conditional_on_supplied_scene_and_bounds`，表示条件式结论 |

协议输入有效但轨迹不可接受时：`status=ok`、`verdict=FAIL`。输入本身非法或跨版本时：`status=error`，没有核验结论，更不能执行。

## 核验顺序

1. 检查输入结构、版本、有效覆盖、轨迹初态与时间网格。
2. 检查零航向/曲率、速度、加速度、停车位置、停车期限与车道意图。
3. 按每段控制量重新计算末端位置和速度，检查动力学残差；停车截止时刻不在采样点上时，也插入相应解析检查。
4. 在已验证的非负速度直线运动下，用两端位置构造整个区间的车身扫掠矩形。
5. 对模型提供的整区间目标占用加位置不确定性，独立计算它与车身扫掠矩形的间距；与 T2 携带的可信配置间距比较。未知区域也按障碍处理。
6. 检查车身在已知道路内，以及参考点扫掠范围在 T2 走廊内。
7. 只有全部通过，才释放请求的短执行前缀。

区间矩形相互比较会丢失区间内的时间相关性，可能保守拒绝一条实际无碰撞的轨迹，但不会因此把不确定区间当成空域。其条件保证依赖目标占用包络确实覆盖真实运动，这一前提必须由 G2 检查。

## 主要核验违例

| 错误码 | 反馈含义 |
|---|---|
| `INITIAL_STATE_MISMATCH` | 轨迹不是从当前自车状态出发 |
| `DYNAMICS_RESIDUAL` | 轨迹不符合声明的分段运动关系 |
| `OBSTACLE_CLEARANCE` | 某区间车身与目标/未知区域间距不足 |
| `ROAD_BOUNDARY` / `CORRIDOR_BOUNDARY` | 超出已知道路/允许走廊 |
| `STOP_BOUNDARY` / `STOP_DEADLINE` | 越过停车参考点上界或未按时停车 |
| `SPEED_LIMIT` / `ACCELERATION_LIMIT` | 车辆运动边界超限 |
| `LANE_INTENT` / `UNSUPPORTED_MOTION` | 不符合指定车道或当前核验剖面 |

违例 `time_s` 对区间碰撞检查表示**问题区间的起始时刻**，不是精确碰撞时刻；位置同样是该区间起点位置。`minimum_clearance_m` 为保守包络间距，不是测量真值。

## 执行与反馈边界

T4 只返回许可数据，不控制车辆。调用端必须确认当前时钟、场景版本与自车初态仍有效，才能把短前缀交给执行器。场景更新后，旧结论自动失去跨轮可用性；需要新一轮核验。

失败反馈交给驾驶智能体，由其修订决策或假设。工具不得降低安全间距“求通过”，不得在失败时切换到另一个驾驶策略。

验收：正常轨迹通过；匀速故障轨迹、采样间截止时刻违例、运动不连续以及伪造宽走廊均须被拒绝。故障请求/响应见 `results/fault_injection.trace.json`。
